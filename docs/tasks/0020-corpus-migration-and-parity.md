# Task 0020: Move the live corpus to CockroachDB, and prove nothing was lost

> [!IMPORTANT]
> This task touches `spoin_db`, which holds real verified production content. Per
> CLAUDE.md, **the owner's explicit approval is required before any non-`SELECT`
> operation, every time** — and that approval does not carry over from one step to the
> next. Reading and exporting are `SELECT`s and are fine. Everything else is gated.
> Nothing in this task deletes, truncates, or modifies `spoin_db`; the migration is a
> copy, and the source stays untouched and authoritative until the cutover
> ([task 0021](0021-cockroachdb-cutover.md)) is signed off.

## The problem

Measured 2026-08-22: `spoin_db` holds **15 topics (7 with generated content), 322
subtopics, 6,884 cards, 5,206 questions, 13 users** across 46 MB. This content was
produced by real generation runs against real quota
([run 2 benchmark](../architecture/generation-pipeline-run-2-benchmark.md)) and the old
mock fixtures were purged deliberately. It is not reproducible cheaply — regenerating
it would cost weeks of free-tier quota.

[ADR-0048](../adr/0048-cockroachdb-over-neon.md) moves the database. This task moves
the content, and — more importantly — proves it arrived intact.

## Why it matters

"The import succeeded" is not the same claim as "the corpus is intact", and the gap
between them is where this goes wrong. Two failure modes specifically:

- **Embeddings.** `card.content_embedding` and `topic.embedding` are `VECTOR(384)`
  floats. A round-trip through a text export that loses precision, reorders
  dimensions, or silently nulls a column produces a database that *looks* complete —
  the cards render, the counts match — while `find_corpus_duplicate` and topic
  matching quietly stop working. Nothing user-facing fails; the generator just starts
  accepting duplicates.
- **User state.** 13 users have real progression: `UserCardState`, `UserTopicProgress`
  with its `tier_unlocked` boolean arrays and quiz-pass flags. Losing a latch means
  revoking earned progress, which ADR-0009's whole design exists to prevent.

## What to do

1. **Export from `spoin_db`, read-only.** `SELECT`-based, per table, in
   foreign-key-safe order. `pg_dump`'s plain schema-only mode is the only form
   CockroachDB accepts — data dumps and custom formats are not supported — so plan on
   a data export you control rather than `pg_dump | psql`. Snapshot to a file first;
   do not stream source-to-destination, because a failed run should leave you with the
   export, not with nothing.
2. **Get owner approval before the first write to CockroachDB.** The target is a new
   empty database, so the risk to `spoin_db` is nil — but the approval gate in
   CLAUDE.md is about the *class* of operation, and asking costs a message.
3. **Import into a CockroachDB database already migrated by task 0018.** Not
   `create_all` — the migrated schema, so what you populate is what production will
   have.
4. **Verify parity, and define it before you run it.** At minimum:
   - Row counts per table, all of them, not just the interesting ones.
   - Referential integrity: no orphaned `card.subtopic_id`, `question.card_id`,
     `user_topic.topic_id`.
   - **Embedding fidelity**: for every row with a non-null embedding, the vector
     round-trips to the same 384 floats. Compare exactly where the export format
     allows it and within a stated tolerance where it does not — and state which,
     because "close enough" without a number is not a verification.
   - **Semantic parity, not just byte parity**: run
     `find_corpus_duplicate`-style cosine queries against both databases for a sample
     of cards and confirm the same nearest neighbour and a distance within tolerance.
     This is the check that catches a technically-successful import of subtly wrong
     vectors.
   - User progression: `tier_unlocked` and `tier_quiz_passed` arrays match per
     (user, topic), element by element.
5. **Write the parity check as a script that can be re-run**, not a session of ad-hoc
   queries. The cutover will want it a second time, and so will whoever doubts the
   result in three months.
6. **Time it, and write the number down.** 46 MB is small; the point of measuring is
   that this is the last time it will be. At 1,000 topics the same operation is ~5 GB,
   and knowing the shape of the curve is what makes the "should we have done this
   earlier" question answerable.

## What to hand back

- The export artifact, and the import + parity scripts, committed.
- The parity report: every check, with its actual numbers, including the ones that
  passed. A report that lists only failures cannot be distinguished from a report
  generated by a script that did not run.
- Wall-clock timings for export, import, and verification.
- `spoin_db` demonstrably unmodified — same row counts and `pg_database_size` before
  and after. Include this in the report.

## Open questions / notes for whoever picks this up

- **Do not "clean up" during the migration.** The temptation to drop the 8 empty topic
  shells, prune the 13 test users, or normalize something in flight is real, and every
  one of those is a `spoin_db` content decision requiring separate owner approval
  (CLAUDE.md is explicit that a soft-delete or a "just cleanup" bulk update is not an
  exception). Move the corpus as-is. Cleanup is a different task with a different
  conversation.
- **The 8 empty topics matter.** `Cloud Native Security`, `Kubernetes`, `Linux Kernel
  Internals` and five others exist as `Topic` rows with zero subtopics — they are
  queued generation targets, not junk. If they vanish, the work queued against them
  vanishes with them.
- **Decide what happens to in-flight `GenerationJob` rows** before starting. A job in
  `running` state at export time has no worker attached on the other side. Neither
  dropping it nor importing it as-is is obviously right; pick one and say why.
- **`avatar_image` blobs** are the only large-per-row data (`LargeBinary`, up to ~5 MB).
  Whatever export format you pick has to handle binary faithfully — a text-mode export
  that mangles `BYTEA` is a classic. Verify at least one avatar byte-for-byte.

## Timebox

Medium. The mechanics are a day at 46 MB; the parity definition in step 4 is the part
that deserves the thought, and it is worth over-investing there because the cutover's
confidence rests entirely on it.
