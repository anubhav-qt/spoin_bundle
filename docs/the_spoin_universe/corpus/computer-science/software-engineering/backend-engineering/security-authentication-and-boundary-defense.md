## Authentication Primitives: Stateful Sessions versus Stateless JSON Web Tokens

Authenticating user requests across HTTP involves two primary primitives:

**Stateful Server Sessions:**
Upon successful authentication, the server generates a cryptographically random session identifier (typically 128 bits of entropy).
- **Transport:** The session ID is transmitted to the client in an HTTP cookie configured with critical security flags: `HttpOnly` (prevents client-side JavaScript access, mitigating Cross-Site Scripting / XSS token theft), `Secure` (restricts transmission strictly to TLS/HTTPS connections), and `SameSite=Lax` or `SameSite=Strict` (prevents cross-site cookie attachment, mitigating Cross-Site Request Forgery / CSRF).
- **Storage:** Session state (user ID, roles, permissions) is stored in a centralized cache (such as Redis) with an expiration interval (TTL).
- **Advantage:** **Instantaneous revocation.** When an administrator bans a user or a user changes their password, deleting the session record in Redis instantly revokes access across all application nodes.

**Stateless JSON Web Tokens (JWT - RFC 7519):**
A JWT encodes claims into three dot-separated Base64URL-encoded segments: `Header.Payload.Signature`.
- **Header:** Declares token type (`typ: "JWT"`) and cryptographic signing algorithm (`alg`), such as HMAC-SHA256 (`HS256`), RSA-SHA256 (`RS256`), or Ed25519 (`EdDSA`).
- **Payload:** Contains identity claims, including standard registered claims: `sub` (subject/user ID), `iss` (issuer URL), `aud` (audience), `exp` (expiration epoch), and `iat` (issued-at epoch).
- **Signature:** Generated by computing the cryptographic hash over `Header.Payload` using a private key or pre-shared secret. Verifying backend services validate the cryptographic signature locally using the issuer's public key (retrieved via JSON Web Key Sets at `/.well-known/jwks.json`), eliminating database lookups on the request path.
- **The Revocation Paradox:** Because a JWT is self-contained and validated cryptographically, a issued token remains completely valid until its `exp` timestamp passes. A compromised user cannot be revoked immediately without maintaining an in-memory blocklist on the backend, which negates the stateless scaling advantage.
- **Production Standard:** Pair **short-lived access tokens** (5 to 15 minute lifespan) with **stateful refresh tokens** stored securely in the database. When an access token expires, the client exchanges the refresh token at an authentication endpoint; if the account has been revoked, the refresh request fails.

## Delegation and Identity: OAuth 2.0 and OpenID Connect

**OAuth 2.0 (RFC 6749):**
OAuth 2.0 is an authorization framework that enables third-party applications to obtain delegated access to HTTP resources without sharing user passwords. OAuth defines four roles: Resource Owner (end user), Resource Server (API hosting data), Client (consuming application), and Authorization Server (identity provider).

The modern security standard for client authentication is the **Authorization Code Flow with PKCE (Proof Key for Code Exchange, RFC 7636)**:
1. The client generates a random cryptographic string called a `code_verifier` and derives a `code_challenge = BASE64URL(SHA256(code_verifier))`.
2. The client redirects the user to the Authorization Server, passing the `code_challenge` and `code_challenge_method = S256`.
3. Following user consent, the Authorization Server returns an `authorization_code`.
4. The client exchanges the `authorization_code` alongside the original plain `code_verifier` for an access token.
5. The Authorization Server hashes the `code_verifier` and verifies that it matches the initial `code_challenge`. This eliminates the threat of intercepted authorization codes on public clients (single-page apps and mobile devices).

**OpenID Connect (OIDC 1.0):**
OAuth 2.0 is strictly an authorization protocol, not an authentication protocol. OpenID Connect extends OAuth 2.0 by introducing an identity layer. The Authorization Server issues a signed **`id_token`** (a JWT) alongside the OAuth access token. The `id_token` provides user identity claims (`sub`, `email`, `name`, `auth_time`), allowing applications to confirm the user's identity securely.

## Authorization Architectures: RBAC versus ABAC

Backend systems enforce access control using two primary architectural paradigms:

- **Role-Based Access Control (RBAC):** Permissions are grouped into discrete roles (e.g. `Administrator`, `Editor`, `Viewer`), and users are assigned one or more roles. The application checks permissions by inspecting user roles (`if user.has_role('Editor')`). RBAC is straightforward to implement, but becomes unwieldy ("role explosion") when business logic requires dynamic, contextual rules.
- **Attribute-Based Access Control (ABAC) and Policy-as-Code:** Evaluates access permissions dynamically by analyzing attributes across four dimensions:
  1. **Subject:** User ID, department, clearance tier.
  2. **Action:** `read`, `create`, `update`, `delete`.
  3. **Resource:** Owner ID, document classification, status.
  4. **Environment:** Request IP, time of day, device security posture.
  Decoupled engines (such as Open Policy Agent / OPA executing Rego policies) evaluate queries like: *"Allow `update` on `Invoice` if `Subject.department == Resource.department` AND `Resource.status == 'draft'` AND `Environment.is_business_hours == true`."*

## Transport Layer Security: TLS 1.3 and Mutual TLS

**TLS 1.3 (RFC 8446, August 2018):**
TLS 1.3 overhauled transport security to optimize handshake latency and eliminate cryptographic vulnerabilities:
- **1-RTT Handshake:** Reduces connection establishment latency from two network round trips (TLS 1.2) to one round trip by transmitting key exchange parameters (`key_share`) in the initial `ClientHello` frame.
- **Pruning Legacy Insecure Primitives:** Completely removed support for static RSA key exchange (which lacked Forward Secrecy; compromising a server private key allowed historical traffic to be decrypted). Removed legacy stream and block ciphers (RC4, CBC-mode, DES, 3DES) and obsolete hash functions (MD5, SHA-1). Mandated Authenticated Encryption with Associated Data (AEAD) ciphers (such as AES-GCM and ChaCha20-Poly1305).
- **0-RTT Early Data Vulnerability:** TLS 1.3 allows returning clients to send application data in the very first packet. **Security Warning:** 0-RTT data has no forward secrecy and is vulnerable to network **replay attacks**. Backend proxies must strictly restrict 0-RTT execution to safe, idempotent `GET` requests, rejecting any non-idempotent mutations (`POST`, `PUT`, `DELETE`).

**Mutual TLS (mTLS):**
While standard TLS authenticates only the server to the client, mTLS requires both the client and server to present and verify X.509 certificates. mTLS is the foundational transport layer for zero-trust microservice communication within service meshes, ensuring that internal service calls cannot be spoofed across internal VPC networks.

## Traffic Shaping and Rate Limiting Algorithms

Rate limiters protect backends from denial-of-service (DoS) attacks, brute-force credential stuffing, and cascading downstream resource exhaustion:

**1. Token Bucket:**
A bucket holds a maximum capacity of $C$ tokens. Tokens are continuously added at a constant fill rate $r$ tokens per second. Each incoming request consumes one token. If the bucket contains $\ge 1$ tokens, the request is allowed; if empty, the request is rejected with HTTP `429 Too Many Requests`.
- **Characteristics:** Accommodates sudden bursts of traffic up to capacity $C$, then smoothly throttles requests to the steady-state rate $r$.

**2. Leaky Bucket:**
Incoming requests enter a FIFO queue holding at most $C$ requests. The bucket leaks (processes) requests at a strictly constant rate $r$. If the queue is full when a new request arrives, it overflows and is dropped.
- **Characteristics:** Completely smooths egress traffic, guaranteeing a steady processing rate to downstream dependencies regardless of bursty arrival patterns.

**3. Sliding Window Counter:**
Mitigates the "boundary burst" flaw of Fixed Window algorithms (where a client exhausts its entire quota in the final second of Window 1 and again in the first second of Window 2, effectively doubling the allowed traffic).
The algorithm maintains counters for the current window and previous window:
$$\text{estimated\_requests} = \text{current\_window\_count} + (\text{previous\_window\_count} \times (1 - \text{fraction\_of\_current\_window\_elapsed}))$$
Provides smooth rate enforcement across time boundaries while consuming negligible memory (two integer counters per client in Redis) compared to sliding window log queues.

## Critical Backend Vulnerability Vectors

The OWASP API Security Top 10 highlights critical architectural vulnerabilities in backend implementations:
- **Broken Object Level Authorization (BOLA / IDOR):** Occurs when endpoints expose entity identifiers (e.g. `GET /api/accounts/1042/statement`) without validating that the authenticated user owns or has permission to view that specific record. Mitigated by enforcing ownership checks within service or database query boundaries (`WHERE account_id = :id AND user_id = :auth_user_id`).
- **Server-Side Request Forgery (SSRF):** Occurs when a backend service fetches a remote URL provided by a client without restricting the destination IP. Attackers supply loopback or link-local addresses (`http://169.254.169.254/latest/meta-data/`) to steal cloud instance metadata, IAM credentials, or internal microservice endpoints. Mitigated by resolving domains, validating that IPs are not private or link-local ranges, and blocking internal routing.
- **SQL / Command Injection:** Occurs when untrusted client strings are concatenated directly into database queries or shell executions. Mitigated strictly by using parameterized queries (prepared statements) and object-relational mapping libraries that separate SQL command structure from data inputs.
