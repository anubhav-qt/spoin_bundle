# Task 0041: three columns have a `server_default` in the database that the models do not declare

> **Status:** found 2026-09-05 while writing ADR-0097's migrations. Not fixed — the
> repair is trivial, but which direction to repair it in is a real question and the
> answer is not obvious from the code.

## What is wrong

Every `alembic revision --autogenerate` run proposes the same three changes, whatever
the actual model change was:

```python
op.alter_column('ask_conversation', 'status',
           existing_type=sa.VARCHAR(length=16), server_default=None, existing_nullable=False)
op.alter_column('ask_message', 'on_topic',
           existing_type=sa.BOOLEAN(), server_default=None, existing_nullable=False)
op.alter_column('generation_job', 'kind',
           existing_type=sa.VARCHAR(length=16), server_default=None, existing_nullable=False)
```

The database has a `server_default` on each (`'active'`, `true`, `'generate'`); the
SQLAlchemy models declare a Python-side `default` instead. Autogenerate sees the
mismatch and offers to drop the database's.

Both migrations for ADR-0097 (`feded8588fd8`, `b9876ddc6238`) were hand-edited to
remove these lines, because dropping a server default is a behaviour change with
nothing to do with embeddings.

## Why it matters more than it looks

It is a **trap for the next autogenerated migration**, not a bug in running code. The
lines look plausible, they appear in every diff, and a session that accepts an
autogenerated file without reading it ships them. The consequence is quiet: a row
inserted by anything that does not go through the ORM — a migration's own `INSERT`, a
hand-written `psql` statement, a future service — would get `NULL` where it used to get
a default, and `NOT NULL` would then reject it.

It also makes every autogenerate diff noisier than it should be, which is how a real
change hides in the noise.

## The work

Decide which side is authoritative, then make them agree:

- **Keep the server defaults** (likely): declare `server_default=` on the three model
  columns to match what the database has. The defaults exist because an earlier
  migration created them deliberately.
- **Or drop them**: accept the autogenerated change once, deliberately, and confirm
  nothing inserts these columns outside the ORM.

Either way the diff goes quiet, which is the point.
