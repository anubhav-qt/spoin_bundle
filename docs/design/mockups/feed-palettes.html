Kubernetes
Pods & scheduler

A pod is the unit of scheduling

Kubernetes never schedules a container. It schedules a pod.

Kubernetes never schedules a container -- it schedules a pod. A pod is one or more containers that share a network namespace and storage volumes; containers in the same pod reach each other on localhost and are always placed on the same node, together, or not at all.

This matters the moment you try to scale: you scale pods, not containers. If you put two things in one pod that need to scale independently, you have made a mistake that is awkward to undo later.

Pods & scheduler

The scheduler filters, then scores

Placement is two phases, and only the first one can fail outright.

Filtering removes nodes that cannot run the pod at all -- insufficient CPU or memory, a taint the pod does not tolerate. If filtering removes every node, the pod stays Pending.

Scoring ranks whatever survived, preferring spread across nodes and better resource fit. Scoring never fails; it only picks a winner.

Distributed Systems
Failure & partial failure

Partial failure is the whole problem

A single machine is up or down. A distributed system is neither.

On one machine, a component is working or it is not, and your process usually finds out immediately. Across machines, some parts work and others do not, and you cannot reliably tell which.

Almost every complication in distributed systems -- retries, idempotency, consensus, timeouts -- exists to cope with that one ambiguity.

Failure & partial failure

A timeout is not a failure detector

It is a guess with a deadline attached.

You cannot distinguish a crashed node from a slow one. All you can do is wait a while and give up. That makes every timeout a tradeoff: too short and healthy nodes look dead; too long and real failures go unnoticed.

There is no correct value, only one tuned to a specific latency distribution -- which is why a timeout copied from another system is usually wrong.
