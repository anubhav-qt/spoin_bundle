# Working in this repo

Read this first, every session — it is the bootstrap. It doesn't restate what the docs
already say; it tells you which docs to read and in what order, gives you the shape of the
codebase fast, and states the rules that don't have a natural home in any one doc. A new
chat should be useful immediately from this file, not spend its first ten minutes
re-deriving context that already exists on disk.

## The database

**`spoin_db_2` is the live database** (the local `.env` points
`SPOIN_DATABASE_URL` at it, and the running stack uses it). **`spoin_db` is the
archived earlier copy** — do not point anything at it, migrate it, or read it expecting
current data. Everything below that says "`spoin_db`" means the live DB, `spoin_db_2`;
the name in the prose is stale and not worth a churny find-replace, but the rule is the
same and applies to `spoin_db_2`.

**The live database is the only one this project uses.** Read-only access — `SELECT`,
inspecting a row, checking whether a migration applied — is fine and often necessary.
**Anything else needs the project owner's explicit approval first, every time, agent
sessions included.** That covers the obvious destructive operations (`alembic downgrade`,
`TRUNCATE`/`DELETE`, `docker compose down -v`, editing a row by hand, pointing the stack at
a different database, re-enabling fixture seeding) and the ones that sound harmless because
they don't feel destructive: a soft-delete, clearing an archive or trash table, a bulk
`UPDATE` framed as cleanup, resetting one user's state to "fix" it. **"It's just trash" or
"it's just one row" is not an exception** — ask first, even when asking feels like
overhead and even when the task would obviously be easier without asking.

`spoin_db` holds real, verified production content generated by the pipeline (see [generation-pipeline-test-run.md](docs/architecture/generation-pipeline-test-run.md), [generation-pipeline-run-2-benchmark.md](docs/architecture/generation-pipeline-run-2-benchmark.md), [generation-pipeline-run-3-benchmark.md](docs/architecture/generation-pipeline-run-3-benchmark.md), [generation-pipeline-run-4-benchmark.md](docs/architecture/generation-pipeline-run-4-benchmark.md), [generation-pipeline-run-5-benchmark.md](docs/architecture/generation-pipeline-run-5-benchmark.md), [generation-pipeline-run-6-benchmark.md](docs/architecture/generation-pipeline-run-6-benchmark.md), [generation-pipeline-run-7-benchmark.md](docs/architecture/generation-pipeline-run-7-benchmark.md), and [generation-pipeline-run-8-benchmark.md](docs/architecture/generation-pipeline-run-8-benchmark.md) for the corpus's growth and the current topic/card/question counts). Old mock/seeded testing fixtures were completely purged. From now on, testing the generation pipeline directly populates and expands the live user corpus with authentic production cards and quiz questions — never re-seed fake data or wipe existing topics without explicit approval. If a task seems to need touching real data, stop and ask instead of proceeding — don't route around the question by finding a technically-different way to get the same effect.

### STRICT: database migration / portability testing is REMOTE-ONLY, never on the local stack

CockroachDB and Neon portability work (tasks 0016 / 0017 / 0019, ADR-0048, and
anything that follows them) is done **directly against a throwaway remote database
the owner provisions** — a CockroachDB Cloud cluster, a Neon branch, or similar.
It is **never** done against the local Docker stack, and never against anything the
local `.env` can reach.

The local Postgres in `docker compose` (the `db` service) **is** production. It
holds `spoin_db_2` — tens of thousands of real cards and quiz questions, the
worker generating into it continuously — and it has been destroyed **three times**
already, so:

**The single most dangerous command is `docker compose down -v` (a.k.a. `make
clean`) — and `docker volume rm` on the `db` volume.** The `db` container's one
volume holds BOTH `spoin_db_2` and the test database `spoin_db_test`
(docker-compose.yml), so wiping the volume takes production with it. NEVER run
`make clean` / `docker compose down -v` / `docker volume rm` on this project.
`docker compose down` **without** `-v` is fine (containers stop, volume kept).

For ANY migration, portability, schema-diff, or DB-engine-comparison task, these
are hard prohibitions — no approval path, do not ask, just don't:

- **Never** run `alembic downgrade`, `alembic stamp`, `TRUNCATE`, `DELETE`,
  `DROP`, a bulk `UPDATE`, `docker compose down -v`, or `docker volume rm`
  against the local stack or any URL from `.env`.
- **Never** run a migration "to test that it applies" against the live DB. Test it
  on the remote throwaway DB the owner gives you.
- **Never** point `SPOIN_DATABASE_URL`, `alembic.ini`, or a test config at the
  live DB for a portability experiment. If you need a database to experiment on
  and the owner has not already handed you a remote URL, **stop and ask for one** —
  do not improvise with the local stack.
- **Never** spin up a "clean" local database by resetting the existing one. A
  clean DB for a *portability* experiment is a fresh remote instance the owner
  provisions.

**Running the normal test suite is safe and is NOT what this section forbids.**
`make test` (→ `docker compose --profile test run --rm test`) points
`SPOIN_TEST_DATABASE_URL` at `spoin_db_test`, a *separate database* in the same
instance; `tests/conftest.py`'s `session` fixture `drop_all`/`create_all`s only
that database's tables and hard-errors (not skips) unless the DB name ends in
`_test`, so it structurally cannot touch `spoin_db_2`. Run the DB-backed tests
that way — never by hand-setting `SPOIN_TEST_DATABASE_URL` to `spoin_db_2` (it
would refuse anyway) and never by running the migration/portability commands
above to "prepare" a DB for them.

Read-only inspection of the live DB (`SELECT`, `\d`, `alembic current`) stays
fine. The line is: reads on `spoin_db_2` local; its writes / schema changes /
engine experiments remote; the test suite on `spoin_db_test` via `make test`.

## The codebase at a glance

```
apps/api      FastAPI (Python 3.13, async). The single source of truth for every client —
              owns all business logic, the DB schema, auth, the quota governor, the feed
              read path, and the generation write path. apps/worker imports this package
              directly; apps/web never does — it only ever speaks HTTP to it, exactly as
              the future React Native app will. If the web client can do something the
              mobile client can't, that's a bug, not a shortcut.
apps/worker   Background jobs. Same codebase as apps/api, a different entrypoint
              (worker/__main__.py) — not a second project. Claims GenerationJob rows and
              runs generation/pipeline/. Nothing here is ever in a user-facing request.
apps/web      Next.js + TypeScript, deployed to Cloudflare Pages. Rendering and client
              state ONLY, zero business logic — see "rules that generalize" below.
docs/         Everything durable that isn't code: architecture, ADRs, tasks, mockups.
              This is where "why" lives; see "Read before doing anything" below.
```

Inside `apps/api/src/spoin/`, roughly in dependency order: `core` (config, DB session) →
`domain` (SQLAlchemy models — the schema everything else inherits) → `api` (routers, wire
schemas, the HTTP surface). Two independent verticals sit on top of that shared base:

- **Read path** — `feed` (candidate generation, seen-filtering, ranking, pagination) and
  `engagement` (event ingest, the seen-state machine). **No LLM call may appear anywhere
  in here, ever** — enforced by `tests/test_architecture.py`, not just stated.
- **Write path** — `generation` (`ContentGenerator`, the LangGraph pipeline, the quota
  governor — the only package allowed to import LangChain/LangGraph, one file each) and
  `embeddings` (local, never a quota'd API). `worker` is the batch entrypoint that drives
  it; `generate_topics.py` is a direct CLI entrypoint that bypasses the job queue.

**Why those two verticals are worth keeping structurally apart:** a swipe is ~50ms; an LLM
call is 2–10 seconds. Cards are generated once by the write path and served to everyone who
qualifies by the read path — personalization is ranking over a shared corpus, never
per-user generation. That single fact is the reason the rest of the architecture looks the
way it does. Full diagram and reasoning:
[`docs/architecture/overview.md`](docs/architecture/overview.md). Per-package depth: each
of `apps/api/README.md`, `apps/worker/README.md`, `apps/web/README.md` states what it owns,
what it doesn't, and where to start reading inside it.

## Read before doing anything

1. [`docs/architecture/overview.md`](docs/architecture/overview.md) — the mental model
   everything else assumes. **The feed read path never touches an LLM** is the one thing
   to internalise before touching code.
2. [`docs/architecture/content-model.md`](docs/architecture/content-model.md) — what a
   card, subtopic, and quiz question actually are. The highest-leverage schema in the
   project; generation, ranking, and the UI all inherit its shape.
3. [`docs/adr/`](docs/adr/) — skim the index, read any ADR whose title touches what you're
   about to change. **Do not re-litigate a decision that has an ADR** without reading its
   "Alternatives considered" first — the reason something looks suboptimal is usually
   written down. An ADR's own header says whether it's been amended or superseded; follow
   that chain before trusting an older one at face value.
4. [`docs/tasks/`](docs/tasks/) — open, self-contained work. Check here before assuming
   something is unstarted or unowned.
5. [`docs/design/mockups/`](docs/design/mockups/) — the feed's visual design is real,
   working HTML, not a picture to redraw from. [ADR-0012](docs/adr/0012-feed-visual-design.md)
   explains the decisions behind it.

If a task touches the feed, engagement, or progression specifically, also read
[ADR-0009](docs/adr/0009-quiz-gated-progression.md), [ADR-0010](docs/adr/0010-feed-serving.md),
and [ADR-0011](docs/adr/0011-engagement.md) before writing code — that trio defines rules
(SEEN semantics, event/state/aggregate separation, ranking inputs) that are easy to
accidentally violate from the UI side without realizing it.

If a task touches **card content, titles, or generation prompts**, read
[ADR-0021](docs/adr/0021-ascii-scene-library.md) and [ADR-0022](docs/adr/0022-dual-titles.md)
first. Same reason: both define rules whose violation is *silent*. Free-form ASCII art and
a single playful `title` both look fine on the handful of cards anyone actually eyeballs,
and degrade everywhere else.

If a task touches **generation reliability** (quota, retries, the LLM call boundary), read
[`docs/architecture/generation-pipeline.md`](docs/architecture/generation-pipeline.md),
[ADR-0028](docs/adr/0028-key-model-quota-ladder.md), and
[ADR-0065](docs/adr/0065-quota-governor-fairness-accounting-and-terminal-states.md) first.
The quota ladder has failure modes that look like content-quality problems until you trace
them back — see the "gate: ... failed" log lines' distinction between a genuine rejection
and a call that never returned a verdict at all. ADR-0065 draws the matching line on the
quota side: `QuotaExhaustedError` is an abstract base, and its three subclasses
(`DailyQuotaExhaustedError`, `AllCellsThrottledError`, `AllModelsUnavailableError`) mean
genuinely different things — a run that "hit quota" may have hit a provider outage with the
day's budget barely touched.

## The rules that generalize

**No business logic in `apps/web`.** The web app talks to `apps/api` over HTTP exactly as
the mobile app will. If the web client can do something the mobile client can't, that's a
bug. When in doubt about whether something belongs in a component or the API, it belongs
in the API.

**The generator is trusted for taste, never for constraints.** Anything that must be
*true* — a column budget, a reuse cap, a character limit, a difficulty rating — is
enforced or independently verified outside the model. Anything that merely needs to be
*good* — prose, a punchline, which scene fits an idea — is the model's job. This is one
rule, not three: it is why the quality gate re-rates difficulty instead of trusting the
self-report (content-model.md), why `archetype` is derived rather than requested
([ADR-0017](docs/adr/0017-card-archetypes.md)), and why ASCII scene reuse is counted
server-side rather than asked for in the prompt
([ADR-0021](docs/adr/0021-ascii-scene-library.md)). When you catch yourself adding a
"please keep this under N characters" line to a prompt, you want a check, not a sentence.

**Silliness lives in the hook layer — title, summary, ASCII art. Never in `body`.** The
product's claim is quiz-gated mastery of true things. A joke in the line that stops a
scroll is charm; a joke in the explanation someone is tested on is noise, and it
undermines the gate checks that operate on `body` as meaning.

**A "failed" outcome and a "rejected" outcome are never the same number.** A generation
call that never returned a verdict (quota exhaustion, a malformed whole-batch response, a
transient provider overload) is not the same fact as content that was judged and found
bad — folding the two together makes a quota-exhausted run misread as a content-quality
catastrophe in a report or a log. Keep them as separate counts, and log the actual failure
reason, not just how many. This bit the generation pipeline for real once (pass-2
verification's failure count silently included call failures); see `pipeline.py`'s
`_process_gate_item` for the fix and the reasoning.

## Code style & conventions

**Python (`apps/api`, `apps/worker`).** `mypy --strict` and `ruff` (line length 100 —
`pyproject.toml`'s `[tool.ruff.lint]` select list) are non-negotiable; `make check` runs
both plus the test suite, and CI runs the same. Fix the type error rather than reaching for
`# type: ignore`.

- **Comments explain *why*, never *what*** — this codebase is rigorous about it. SQLAlchemy
  model fields carry `#:` (Sphinx-style) comments that record provenance and cite the ADR
  behind a field's shape; `domain/models/card.py` is the canonical example. A module
  docstring names the doc that explains the file's purpose rather than re-explaining it
  inline. If a comment restates the line under it, delete the comment.
- **A hard architectural rule gets enforced twice, never documented once.** A `ruff`
  `banned-api` entry stops a stray import before the code even runs; an AST-level test in
  `tests/test_architecture.py` catches it in CI even if lint gets bypassed locally.
  ADR-0002's "only `langchain_impl.py` imports LangChain" and hard rule 1 ("no LLM in the
  feed read path") are both wired this way. When you add a rule of this shape, wire it the
  same way — a rule stated only in a doc is a wish, same principle as "generator trusted for
  taste, not constraints" above.
- **Tests prefer the real Postgres `session` fixture over mocking the database** whenever
  the database's own behavior — a unique constraint, a `day`-scoped ledger row, an
  `ondelete=CASCADE` — is the actual thing under test (see `test_quota_governor.py`). Mock
  the generator (`fake.py`, or a mocked `ChatGoogleGenerativeAI`), not the database whose
  behavior you're trying to verify.
- **Every LLM-facing interface method takes a collection, never a single item**
  ([ADR-0005](docs/adr/0005-batch-llm-calls.md)), enforced in `test_architecture.py`. Don't
  add a single-item convenience wrapper "just this once" — the free tier meters requests,
  not tokens, and that's the whole reason the rule exists.

**TypeScript (`apps/web`).** `apps/web/lib/api.ts` is the **only** file that knows the API
exists — every HTTP call goes through the `api` object, grouped by domain
(`// -- Auth --`, `// -- Feed --`, …). Never call `fetch()` from a component. Interface
fields get a `/** ... */` comment when their meaning isn't obvious from the name alone,
usually citing the ADR or invariant behind it (see `TopicRequestResult.status`,
`EngagementEvent.id` for examples) — same "why, not what" discipline as the Python side.
Hand-written types in `lib/api.ts` are placeholders; `packages/api-types` (generated from
the live OpenAPI schema, `make api-types`) is the real source, CI-checked for drift. Don't
hand-maintain a type the generator already owns.

**Everywhere.** No comment a competent reader wouldn't need — the exception this codebase
leans on hardest is a hidden constraint, a subtle invariant, or the ADR that explains why
the obvious-looking alternative was rejected. Grep for `see ADR-` or `content-model.md` in
the source to calibrate the density expected.

## Keep the loop closed

This file and the docs it points at are what make a *new* chat efficient — there is no
memory carried between sessions other than what's written down. That only holds if it
stays current:

- **A decision with real reasoning behind it gets an ADR**, not just a comment in code.
  Use [`docs/adr/TEMPLATE.md`](docs/adr/TEMPLATE.md). Number sequentially; check the
  highest existing number in `docs/adr/` first.
- **A decision that changes or partially supersedes an earlier ADR should say so in both
  directions** — a note in the new ADR pointing back, and a note in the old one (or in
  whichever doc stated the superseded rule) pointing forward. Don't silently leave the old
  doc claiming something the code no longer does — see how
  [ADR-0012](docs/adr/0012-feed-visual-design.md) and
  [content-model.md](docs/architecture/content-model.md)'s "Got it" section reference each
  other for the pattern.
- **Deferred work gets a task doc**, not a TODO comment or a line in a chat that will be
  gone next session. Add it to the table in [`docs/tasks/README.md`](docs/tasks/README.md).
- **A visual design decision gets its source-of-truth mockup committed** under
  `docs/design/mockups/`, not left living only in a chat-published artifact link. Artifact
  links are for review during a session; the committed file is what the next session reads.
- **If something in the docs turns out to be stale while you're working**, fix it in the
  same session rather than noting it and moving on. A doc that's wrong is worse than no doc
  — it actively costs the next session time instead of saving it.

## Stack quick reference

See the README for the full table. The short version: FastAPI + SQLAlchemy async on
Postgres/pgvector, Next.js + TypeScript on the web side, generation behind a
`ContentGenerator` interface, everything free-tier-first (ADR-0003) until it isn't.

`docker compose up` brings up the full stack against `spoin_db`, blank by default — see
"The database" above before assuming you can reset or repopulate it yourself.
